## Architectural findings (the `/nexus` analysis)

Measured, not recalled: **17 workflows in this repo, zero trigger on push to main.** Every
quality gate is `pull_request`-only, which is why main broke twice this week unobserved.

Root cause across every near-miss: **nothing in this estate reasons about what a change can
reach.** Scanners read one file's text; reviewers read a diff; the review-dimensions matrix
tiers risk by where the edit lands and omits `scripts/` entirely. The danger was never in the
lines written — `gate_tests` was 3 lines, `vitest` truncates the tables; `gate_build_full` is
1 line, `build.sh:48` deploys migrations.

Second finding: **reviewer instances have correlated blind spots.** Two same-family reviews
passed the data-loss bug; a fresh instance caught it. More review does not decorrelate — a
different *question* does.

Ranked fixes proposed (not built, and explicitly needing independent design first):
1. Make verification contexts structurally unable to reach a real database (force
   `DATABASE_URL` to a sentinel) — converts a review question into an impossibility.
2. Gate on blast radius: static rule over transitive calls from changed lines against a
   destructive-symbol list (`deleteMany`, `migrate deploy`, `$executeRaw`, paid APIs, email).
3. Run the guards on push to main.
4. For destructive-capability diffs, brief one reviewer with the inverted question.
5. Tier process weight so the heavy path is affordable.
